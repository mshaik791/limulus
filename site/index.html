Most controls check a payment and hope something downstream honours the answer. We create the payment frozen at the bank first, so the verdict is the thing that moves the money — or doesn't.

Two ways in, and one door left unlocked on purpose

A REST API if you own the payment path, an MCP server if your agent is the one holding the tools. Receipt verification takes no key at all — anyone handed a receipt has to be able to check it.

REST API

One call decides. POST /v1/gate also creates the transfer at the rail first and releases or cancels it for you — the path we recommend.

  • POST/v1/gatecreate held, decide, release
  • POST/v1/decisionsverdict only
  • POST/v1/releaserelease a held transfer
  • POST/v1/qualificationsissue, scoped
  • POST/v1/settlementsreport the outcome
  • POST/v1/rails/reconcilefind drift
  • POST/v1/lab/runsrun the scenario pack
  • GET/v1/receipts/:idfetch a receipt
  • OPEN/v1/receipts/verifyno API key

MCP server

JSON-RPC 2.0 over stdio, protocol 2025-06-18. Seven tools. Note what is missing — nothing here sets policy or issues a qualification, so an agent cannot widen its own authority.

  • TOOLcheck_paymenta question, not a payment
  • TOOLpay_invoiceheld, decided, released
  • TOOLget_authorizationwhat a person approved
  • TOOLget_qualificationyour own scope
  • TOOLget_receiptproof of a decision
  • TOOLreport_settlementtell us what happened
  • TOOLverify_receiptcheck anyone's receipt
  • NONEset_policydeliberately absent
  • NONEissue_qualificationdeliberately absent

Receipt verification

Every decision is appended to a SHA-256 hash chain and signed with Ed25519 over canonical JSON. This endpoint takes no API key, because a receipt only we can check is not evidence.

  • OPEN/v1/receipts/verifyno auth, ever
  • GET/v1/records/:idthe chain entry
  • TOOLverify_receiptsame check, over MCP

Offline is the point: the signature, the chain position and the canonical body all travel inside the receipt. A public key and twenty lines of code are enough to check one.

curl -X POST https://api.limulus.dev/v1/receipts/verify \
  -d @receipt.json          # note: no Authorization header

    Our duplicate check read "PO 44812" and "PO-44812" as different orders. A real agent found that, not us. We would rather publish it than have a customer discover it.

    What we are not claiming

    A prototype that oversells itself is worth less than one that doesn't.

    • No customers and no production traffic. Everything on this page ran against the Increase sandbox. We are two payments engineers who have watched this problem from inside a large processor.
    • Agents are not reckless. We tried hard to make them pay fraudulent invoices and failed. Every loss we could produce was a reconciliation failure, not a judgment failure. That is the thesis: models are good at judgment and bad at bookkeeping, and the gate is bookkeeping.
    • Small samples lie, including ours. The duplicate above failed 5/5 in two separate runs. At twenty trials the real rate is half. Both samples agreed with each other and both were wrong — five trials only detects failure rates above about 40%.
    • We found eight bugs in our own gate. A malformed account argument was treated as fraud. A rail outage was indistinguishable from a refusal. Following our own documented flow made payment impossible — and a real Claude agent is what caught it.
    • Nineteen scenarios still need rewriting by hand. They convert badly into the simulated world, so they are excluded from the pack and named in the source rather than quietly dropped.
