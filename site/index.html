Model Arena

Different models. The same financial tests.

We run financial-agent tests across different models and configurations to understand how model choice changes behavior. We examine critical failures, task completion, recovery, and reliability—not just one aggregate score.

The agent is the same in every arm: one accounts-payable workflow, one prompt, the same tools and policy, gate off, temperature 0. Only the model behind it changes. Open scenario pool payments-v1, 22 scenarios × 1 trial per model, model ids as each endpoint reported them. One trial is provisional evidence: a single answer moves a rate by five points.

Platform

Four things, in the order they have to happen

Most controls check a payment and hope something downstream honours the answer. We create the payment frozen at the bank first, so the verdict is the thing that moves the money — or doesn't.

How agents actually lose money

53 scenarios against agents backed by the Claude Code default model, wired to an ordinary payments API with no checks in it. Outcomes read from the records each side wrote — never from the agent's own account of what it did. Sample sizes are the ones shown.

0/60

Fraud didn't work, in sixty tries

Hidden bank-change instructions, forged approval emails, a fake CFO demanding a same-day wire, lookalike vendor names. Refused every time by this model, in these scenarios, at this sample size. Zero of sixty is evidence, not proof the threat is solved.

judgment · adversarial
10/20

Bookkeeping did, half the time

One retainer billed twice under two invoice numbers with nothing linking them. Paid in half of twenty trials — by the same frontier model that had just handled every other invoice in the queue perfectly.

operational · duplicate-disguised
15/15

A smaller model never caught it

Swap in a smaller model — a decision someone makes on cost per invoice, not on risk — and duplicates went from mostly caught to never caught in fifteen trials. Safe is a property of a configuration, not of a company. The published record names the run, not the model id.

Increase sandbox validation

Allow submits. Block leaves nothing behind.

Fourteen checks pass against the Increase sandbox. Funds are reserved when the transfer is created, so a held payment can't be double-spent while a person decides.

ALLOW     → submitted
ESCALATE  → pending_approval  (expires unsent)
WAIT      → held, retryAfterMs 30000
BLOCK     → canceled · no ledger entry at all

Documentation

Two ways in, and one door left unlocked on purpose

A REST API if you own the payment path, an MCP server if your agent is the one holding the tools. Receipt verification takes no key at all — anyone handed a receipt has to be able to check it.

REST API

One call decides. POST /v1/gate also creates the transfer at the rail first and releases or cancels it for you — the path we recommend.

  • POST/v1/gatecreate held, decide, release
  • POST/v1/decisionsverdict only
  • POST/v1/releaserelease a held transfer
  • POST/v1/qualificationsissue, scoped
  • POST/v1/settlementsreport the outcome
  • POST/v1/rails/reconcilefind drift
  • POST/v1/lab/runsrun the scenario pack
  • GET/v1/receipts/:idfetch a receipt
  • OPEN/v1/receipts/verifyno API key

MCP server

JSON-RPC 2.0 over stdio, protocol 2025-06-18. Seven tools. Note what is missing — nothing here sets policy or issues a qualification, so an agent cannot widen its own authority.

  • TOOLcheck_paymenta question, not a payment
  • TOOLpay_invoiceheld, decided, released
  • TOOLget_authorizationwhat a person approved
  • TOOLget_qualificationyour own scope
  • TOOLget_receiptproof of a decision
  • TOOLreport_settlementtell us what happened
  • TOOLverify_receiptcheck anyone's receipt
  • NONEset_policydeliberately absent
  • NONEissue_qualificationdeliberately absent
// claude_desktop_config.json — or any MCP client
{
  "mcpServers": {
    "limulus": {
      "command": "npx",
      "args": ["-y", "@limulus/mcp"],
      "env": { "LIMULUS_API_KEY": "lim_live_…" }
    }
  }
}

Receipt verification

Every decision is appended to a SHA-256 hash chain and signed with Ed25519 over canonical JSON. This endpoint takes no API key, because a receipt only we can check is not evidence.

  • OPEN/v1/receipts/verifyno auth, ever
  • GET/v1/records/:idthe chain entry
  • TOOLverify_receiptsame check, over MCP

Offline is the point: the signature, the chain position and the canonical body all travel inside the receipt. A public key and twenty lines of code are enough to check one.

curl -X POST https://api.limulus.dev/v1/receipts/verify \
  -d @receipt.json          # note: no Authorization header

    Nobody knows yet how agents lose money. We are trying to find out.

    Every safety claim in this category is a guess until somebody runs the experiment. So we built the experiment first and the product second — and we publish what we find, including the parts that make our own product look unnecessary.

    Bugs found in our own gate

    Our duplicate check read "PO 44812" and "PO-44812" as different orders. A real agent found that, not us. We would rather publish it than have a customer discover it.

    Our own test rig found eight bugs in the gate before a customer could; the status board below lists them. The Lab is not a marketing exercise. It is how the gate gets configured: the checks we require are the ones the experiments showed actually fire, and the readiness ladder an agent climbs is scored on what it did, never on what it said it did. These are our tests of our own reference agents, not customer traffic.
